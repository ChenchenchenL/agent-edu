# 代码审查模板

用于以下场景：

- 询问代码完成度
- 询问设计缺陷
- 询问实现质量、可维护性、回归风险

## 输出原则

- 使用批判性、直接的语气
- 先讲问题，再讲结论
- 优先指出缺口、风险、错误假设、未覆盖区域
- 每个问题都给出证据：文件、行号、行为、缺失测试、边界条件
- 没有明显问题时，也要明确剩余风险和未验证项

## 推荐结构

### 1. Findings

按严重度排序列出问题。

示例格式：

- 高严重度：[path/to/file.py:123] 某处在输入为空时会触发错误分支，但当前没有边界校验，实际运行会返回 500 而不是受控错误。
- 中严重度：[path/to/service.ts:88] 这里把领域规则写进了路由层，破坏了应用层边界，后续复用和审计会继续恶化。
- 低严重度：[path/to/test_file.py:45] 只覆盖了成功路径，没有覆盖失败路径和回滚行为，回归风险没有被真正压住。

### 2. Open Questions / Assumptions

- 哪些外部前置条件被默认成立，但代码里没有验证？
- 哪些“以后再补”的部分会直接影响当前结论？
- 哪些行为依赖人工约定而不是程序保证？

### 3. Residual Risks / Change Summary

- 如果没有修复上述问题，最可能出现什么故障？
- 哪些检查没有跑，导致结论只能是部分成立？
- 当前实现离“完成”还差哪些明确项目？

## 禁止写法

- 不要先说“整体不错”再轻描淡写提问题
- 不要用模糊表述替代证据
- 不要把缺少测试、边界校验、架构越层说成“小问题”
- 不要在未验证完成度时直接下“已经完善”结论
